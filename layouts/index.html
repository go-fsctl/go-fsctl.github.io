Why go-fsctl

Straight to the kernel, and nothing in between.

Every module talks to the kernel the way the reference CLI does — by opening a control device and issuing the subsystem's ioctls. What that removes is not just a dependency; it is a parser for output nobody promised to keep stable.

⚙️

No subprocess, no scraping

No losetup, dmsetup, btrfs(8) or libzfs to install, and no output format to re-learn when it changes. A missing binary cannot break a program that never ran one.

🧩

Independent modules

Each is its own Go module with no dependency on the others and none outside the standard library. Take loop without taking a filesystem stack.

🚫

CGO_ENABLED=0

No C toolchain, so cross-compiling is the ordinary Go story and a static binary stays static. The kernel interface is a syscall, which Go can make by itself.

📐

Coverage gated, not reported

{{ len (where .Site.Data.repos.modules "gate" true) }} of {{ len .Site.Data.repos.modules }} modules fail CI under 100% — a floor the workflow enforces rather than a number in a badge. blk is the exception: vet, tests, the race detector and cross-builds, without a coverage gate.

💽

Not only Linux

The ioctl modules are Linux, as their subsystems are. cowclone also speaks APFS clonefile(2) on macOS and falls back to a byte copy anywhere else, so one call works wherever the program runs.

🧪

A test that cannot run says so

The integration tests drive real kernel objects — /dev/loop-control, a device-mapper target — and skip when the device is absent or the process is not root, rather than passing against a mock. A green run on a machine without them is honest about what it did not prove.
